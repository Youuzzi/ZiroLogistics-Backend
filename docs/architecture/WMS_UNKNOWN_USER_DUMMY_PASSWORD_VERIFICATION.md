# WMS Unknown-User Dummy Password Verification

**Status:** Implemented and wired into `WmsCredentialAuthenticationService` for unknown-account password verification. Unit and MySQL credential-authentication tests cover the integration; this component does not own the complete login workflow.  
**Scope:** Reduce password-hash timing differences between unknown and known email paths.  
**Runtime:** WMS profile only.

## Behavior

- At WMS component construction, generate a cryptographically random 48-byte dummy password.
- Hash it once using the qualified `wmsPasswordEncoder` bean (the configured WMS Argon2id encoder).
- For an unknown email, call `performDummyVerification(submittedPassword)` after the shared login throttle has admitted the request.
- The verifier calls `PasswordEncoder.matches` against the dummy hash and discards the boolean result. It never returns an authentication decision.
- The same process-local dummy hash is reused for the lifetime of the application instance; it is regenerated on restart.
- The generated byte buffer is cleared after encoding. The dummy hash is never logged or exposed.

## Required future login orchestration

1. Apply source/account throttle before user lookup and password work.
2. If the user exists, verify the submitted password against that user's stored hash.
3. If the user does not exist, perform dummy verification using this component.
4. Treat both invalid-password and unknown-user outcomes as the same generic authentication failure.
5. Record the account failure through `WmsLoginThrottleService` after password work.
6. Do not issue a token for an unknown user.

The caller must not skip dummy verification for unknown users or return distinguishable messages/status codes. This component alone does not guarantee perfectly identical request timing: database lookup cost, cache behavior, network scheduling, and other request-path differences still require review and measurement.

## Boundaries

- WMS-only Spring component; no legacy runtime activation.
- No login endpoint, user lookup change, token issuance, or HTTP response mapping.
- No database, schema, V1/V2 migration, Redis, or throttle policy changes.
- No raw password, dummy password, hash, email, or IP logging.
- Unit tests use a recording PasswordEncoder and do not access a database.
